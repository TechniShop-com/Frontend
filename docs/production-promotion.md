# Production promotion

Changes reach `main` through a reviewed pull request and the required `smoke` check. A push to `main` runs the build, Python tests, and browser smoke tests against that commit, but does not promote it. To release, run **Production smoke tests** manually on `main` with `promote` selected. The workflow runs the tests against that commit again and, only after they pass, pushes it directly to `prod`. There is no production pull request or additional production test after the push.

The promotion job fetches `main` and `prod`, fails if `main` has already advanced, and refuses to update `prod` unless its existing commit is an ancestor of the tested commit. The push is a normal fast-forward push; it is not forced. A new `main` commit can arrive between the final fetch and the push, so an older tested commit may be promoted. Run the workflow again manually to promote a newer commit. If `prod` changes concurrently, Git rejects a non-fast-forward push.

## Initial rollout

1. Review and merge these workflow changes into `main` through a pull request. Do not manually run the old direct-push workflow before configuring the protection exception below.
2. Register a dedicated GitHub App and install it on this repository only. Grant repository permission **Contents: read and write**, plus the default read-only metadata access. Store its client ID in the repository variable `PRODUCTION_PROMOTION_APP_CLIENT_ID` and its private key in the repository secret `PRODUCTION_PROMOTION_APP_PRIVATE_KEY`. The workflow creates a short-lived token scoped to the current repository and the contents permission. App registration or installation can require an organization owner's participation.
3. Keep `main` protected with one approving review and the `smoke` check. In the existing classic protection for `prod`, require a pull request, one approving review and the `smoke` status check, and add only the dedicated promotion app to `required_pull_request_reviews.bypass_pull_request_allowances.apps`. Keep administrator enforcement enabled and do not grant other actors an exception. The app bypasses the pull request requirement; the required `smoke` check still applies to the tested commit. The workflow refuses non-fast-forward updates, but protect the app's private key: possession of its credentials grants the app's configured exception.
4. After the workflow lands on `main` and the app and branch rules are configured, run **Production smoke tests** manually on `main` with `promote` selected to release. Without `promote`, a manual run only tests the commit. Pushing or merging into `main` never starts a promotion.
5. Verify a promotion end to end: the main tests pass, `prod` advances to the tested commit, ordinary direct pushes remain blocked, and the intended production deployment starts. Test a promotion that changes a GitHub Actions workflow file too. If GitHub rejects that push for insufficient workflow permission, the app installation and token may additionally need **Workflows: read and write**; verify this before granting it.

If tests fail, `prod` is not an ancestor of the tested commit, or a push fails, inspect the workflow run and branch history before retrying. GitHub suppresses most workflow events caused by `GITHUB_TOKEN`: if another Actions workflow merges a pull request into `main` with that token, its push may not start the `main` smoke run. Verify the deployment integration during rollout.
